## Activate stable upstream propagation

Once the customization and its regression checks are reviewed, integrate them and the sync workflow into the fork default branch using a merge commit. Keep `upstream/main` as the local Git tracking ref for upstream development. The workflow tracks the latest official stable release separately through candidate branches named for their release commits and merge ancestry. It polls daily, with a manual dry run in Actions. It creates a draft PR for a new release commit, records the local merge preflight, and skips releases already in the base or already proposed. Workflow file changes require a manual sync. [GitHub workflow](../.github/workflows/upstream-release.yml)

Fork Actions and GitHub-token PR creation were enabled at inspection. Verify that **Check official OEPL releases** is enabled after merging, then run it with **Dry run** on the default branch. The expected current result is that 3.0.0 is already included. Resolve conflicts on the candidate branch before running PR checks. Approve the bot PR's CI if GitHub holds the runs. Before accepting any update, verify the fork's runtime regression matrix, HACS and hassfest checks, and review any storage, migration, workflow, or dependency changes. Use a merge commit to retain upstream ancestry. The fork blocks inherited upstream publishing jobs. [GitHub token workflow rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

GitHub disables scheduled workflows in public repositories after 60 days without repository activity. Check the last run date if the fork has been quiet and re-enable the schedule or run it manually if needed. [GitHub schedule rules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

Publish manually from a reviewed commit with a distinct, increasing fork version. A calendar version such as `2026.11.1` keeps fork tags separate from upstream release numbers. Match the manifest version to the release tag and put the official release tag and commit, supported HA versions, and rollback version in the release notes. Keep the previous release accessible.

## Rehearse the HACS cutover and rollback

1. Verify that a fresh HA backup includes configuration, registries, and the local Recorder database if used, and that its encryption key is available. For an external Recorder, use its backup procedure. Keep a separate copy of the exact installed component directory for code rollback. Upstream 3.0.0 alone would drop the locally installed multi-hub patch. Take a private baseline of entry IDs, options, device and entity registry identities, disabled items, HA services, and history. Include the OEPL tag store, tag types cache, and cached images in recovery coverage. [HA backups](https://www.home-assistant.io/common-tasks/general/#backups)
2. Rehearse with a synthetic existing entry in the sandbox, then preflight the approved fork release in HACS. Both repositories install into `custom_components/open_epaper_link`. Use **Remove** on the old source in **HACS**, add the fork as a custom integration repository, and download the reviewed release. Install the replacement files before restarting or reloading OEPL. If the download fails, restore the exact installed directory before restarting. [HACS removal](https://www.hacs.xyz/docs/use/repositories/dashboard/#removing-a-repository) · [HACS install path](https://github.com/hacs/integration/blob/2.0.5/custom_components/hacs/repositories/integration.py#L31-L42)
3. Leave all **Devices & services** entries in place. Deleting an entry clears its registry associations. Deleting the last one can also remove `.storage/open_epaper_link_tags`, `.storage/open_epaper_link_tagtypes`, the legacy tag-types cache, and `www/open_epaper_link`. The fork keeps legacy OpenDisplay entries and shows a setup error pointing to their dedicated integration. Inventory any automation targeting the HACS update entity separately because that entity belongs to the repository. [Registry cleanup](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/config_entries.py#L2088-L2126) · [OEPL entry cleanup](https://github.com/OpenEPaperLink/Home_Assistant_Integration/blob/3.0.0/custom_components/open_epaper_link/__init__.py#L489-L565)
4. Restart once after verifying the component directory is complete and the fork is the sole installed source. Compare identities, options, history, services, dashboard and automation targets, and real tag behavior against the baseline. Rehearse reversing the source switch and restoring the previous artifact while retaining the config entries. Code-only rollback requires the previous code to read the resulting stores and entry data. If data or identity changes unexpectedly, stop and evaluate backup recovery before making further changes.
5. Complete the source switch while running HACS, before upgrading to Core 2026.11. In the 2026.11 sandbox, verify that the installed fork and repository migrate into **Settings → Marketplace**, and rehearse rollback to a prior compatible release from the same fork. Marketplace rejects installing a second repository with the same domain and requires removing existing config entries to uninstall the first. Preserve those entries and leave **Delete and uninstall** unused. An entry-preserving source switch directly in Marketplace needs separate verification. [HACS migration to Marketplace](https://www.home-assistant.io/integrations/marketplace/#coming-from-hacs) · [Marketplace uninstall behavior](https://www.home-assistant.io/integrations/marketplace/#uninstalling-a-repository)

Before restarting with the fork, identify which AP owns each tag's content and pause automations that write images or change content. After the restart, configure each secondary content owner in the integration options and verify routing with one test tag before resuming the automations. The installed patch routes uploads by radio IP. The fork routes writes by content owner and requires an explicit destination when the primary reports Remote AP mode. [Firmware upload behavior](https://github.com/OpenEPaperLink/OpenEPaperLink/blob/2.91/ESP32_AP-Flasher/src/web.cpp#L949-L958)

## Validation

- Local Git repositories with a simulated GitHub CLI passed eight sync scenarios. These covered an integrated release, clean dry run, draft PR creation, duplicate PR, conflicted dry run and draft PR, workflow-file change, and invalid tag. Both default branches stayed at the original commit.
- Core 2026.9.4 in a disposable Linux HA Container passed all 32 AP migration and regression tests. These include entry setup, a secondary-only reload, registry identity and store preservation, and unload. The full suite returned 75 passes and 11 drawing snapshot failures. Unmodified official main reproduced the same 11 drawing failures in the same environment.
- The 11 inherited text references were refreshed from the pinned Linux Home Assistant 2026.9.4 CI image. Side-by-side review confirmed matching text, wrapping, anchors, and blank-line placement. The original pixel-exact assertions passed all 54 drawing cases with the refreshed references. [Reference generation and verification](https://github.com/DrBlokmeister/Home_Assistant_Integration/actions/runs/42576098217)
- Core 2026.11.0 in a separate Linux HA Container passed 22 connection, routing, preview, and diagnostics tests. The current-Core run used its installed Core APIs without the config-entry fixture plugin.
- HACS and Marketplace source-switch rehearsal, physical AP testing, and publishing a reviewed release remain separate steps.
