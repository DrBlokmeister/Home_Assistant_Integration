## Activate stable upstream propagation

Once the customization and its regression checks are reviewed, integrate them and the sync workflow into the fork default branch using a merge commit. Keep `upstream/main` as the local Git tracking ref for upstream development. The workflow tracks the latest official stable release separately through candidate branches named for their release commits and merge ancestry. It polls daily, with a manual dry run in Actions. It creates a draft PR for a new release commit, records the local merge preflight, and skips releases already in the base or already proposed. Workflow file changes require a manual sync. [GitHub workflow](../.github/workflows/upstream-release.yml)

Fork Actions and GitHub-token PR creation were enabled at inspection. Verify that **Check official OEPL releases** is enabled after merging, then run it with **Dry run** on the default branch. The expected current result is that 3.0.0 is already included. Resolve conflicts on the candidate branch before running PR checks. Approve the bot PR's CI if GitHub holds the runs. Before accepting any update, verify the fork's runtime regression matrix, HACS and hassfest checks, and review any storage, migration, workflow, or dependency changes. Use a merge commit to retain upstream ancestry. The fork blocks inherited upstream publishing jobs. [GitHub token workflow rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

GitHub disables scheduled workflows in public repositories after 60 days without repository activity. Check the last run date if the fork has been quiet and re-enable the schedule or run it manually if needed. [GitHub schedule rules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

Publish manually from a reviewed commit with a distinct, increasing fork version. A calendar version such as `2026.11.1` keeps fork tags separate from upstream release numbers. Match the manifest version to the release tag and put the official release tag and commit, supported HA versions, and rollback version in the release notes. Keep the previous release accessible.

1. Verify that a fresh HA backup includes configuration, registries, and the local Recorder database if used, and that its encryption key is available. For an external Recorder, use its backup procedure. Keep a separate copy of the exact installed component directory for code rollback. Upstream 3.0.0 alone would drop the locally installed multi-hub patch. Take a private baseline of entry IDs, options, device and entity registry identities, disabled items, HA services, and history. Include the OEPL tag store, tag types cache, and cached images in recovery coverage. [HA backups](https://www.home-assistant.io/common-tasks/general/#backups)
2. Rehearse with a synthetic existing entry in the sandbox, then preflight the approved fork release in HACS. Both repositories install into `custom_components/open_epaper_link`. Use **Remove** on the old source in **HACS**, add the fork as a custom integration repository, and download the reviewed release. Install the replacement files before restarting or reloading OEPL. If the download fails, restore the exact installed directory before restarting. Deleting the last one can also remove `.storage/open_epaper_link_tags`, `.storage/open_epaper_link_tagtypes`, the legacy tag-types cache, and `www/open_epaper_link`. Check for any legacy OpenDisplay OEPL BLE entries before cutover because upstream 3.0.0 has startup cleanup for those entries. Inventory any automation targeting the HACS update entity separately because that entity belongs to the repository. [Registry cleanup](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/config_entries.py#L2088-L2126) · [OEPL entry cleanup](https://github.com/OpenEPaperLink/Home_Assistant_Integration/blob/3.0.0/custom_components/open_epaper_link/__init__.py#L489-L565) · [Legacy BLE cleanup](https://github.com/OpenEPaperLink/Home_Assistant_Integration/blob/3.0.0/custom_components/open_epaper_link/__init__.py#L208-L237)

5. Complete the source switch while running HACS, before upgrading to Core 2026.11.
